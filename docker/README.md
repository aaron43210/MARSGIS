# `docker/` — runtime-mounted assets & build-context convention

This directory holds **runtime-mounted** assets only — files bind-mounted into a
running container, never baked into an image. Keeping them here lets each image
keep a tight, per-service build context.

```
docker/
  postgres/initdb/01-postgis.sql   # mounted into the db container's init hook
```

## Build-context convention

Each image is built from its **own** service directory so contexts stay small
and no sibling concern's tree leaks into a build:

| Image             | Context      | Dockerfile            |
| ----------------- | ------------ | --------------------- |
| `marsgis-engine`  | `./engine`   | `engine/Dockerfile`   |
| `marsgis-backend` | `./backend`  | `backend/Dockerfile`  |
| `marsgis-frontend`| `./frontend` | `frontend/Dockerfile` |

### Shared-contract files owned by the infra concern (but nested in service dirs)

These live inside sibling service directories because they are COPYed into those
images at build time, yet they are owned and maintained by the infra concern.
Application-source units must **not** create or edit them:

- `engine/Dockerfile`, `engine/.dockerignore`
- `backend/Dockerfile`, `backend/.dockerignore`, `backend/entrypoint.sh`
- `frontend/Dockerfile`, `frontend/.dockerignore`, `frontend/nginx/default.conf.template`

## PostgreSQL / PostGIS bootstrap

`postgres/initdb/01-postgis.sql` runs **once**, via the stock
`/docker-entrypoint-initdb.d` hook, the first time the `pgdata` volume is empty.
It enables the `postgis` and `postgis_raster` extensions. Dropping the `pgdata`
volume (`make clean` / `docker compose down -v`) re-runs it on the next `up`.

## Apple Silicon (arm64) note

`postgis/postgis:17-3.5` is published for `linux/amd64` only, so the `db` service
sets `platform: linux/amd64` and runs under emulation on an arm64 Mac (slower, but
Postgres is not performance-critical locally). For a **native arm64** image, swap
the `db` image in `docker-compose.yml` and remove the `platform` line:

```yaml
  db:
    image: imresamu/postgis:17-3.5   # arm64-native drop-in for postgis/postgis:17-3.5
```

CI runs on amd64 runners regardless, so the pinned `postgis/postgis:17-3.5`
remains authoritative there.

## Lockfiles (`--require-hashes`)

The engine and backend Dockerfiles install from `requirements.lock.txt` with
`pip install --require-hashes` **when that lockfile is present**, and otherwise
fall back to the pinned (but unhashed) `requirements.txt`. The hash-locked
lockfiles are generated by the integrator against the pinned Python 3.12 image:

```bash
pip install pip-tools
pip-compile --generate-hashes -o engine/requirements.lock.txt  engine/requirements.txt
pip-compile --generate-hashes -o backend/requirements.lock.txt backend/requirements.txt
```

Fabricating hashes offline would break installs, so the committed `requirements.txt`
files intentionally ship pins without hashes until the lockfile is produced.
